## 问题 1：滚到「对比 / 沙盒 / 时间轴」时导航高亮不跟随

### 根因

`src/components/Sections2.tsx` 的 `Chrome` 组件里，滚动判定用的章节列表是手写死的：

```js
const sections = ['top', 'pipeline', 'funnel', 'stats', 'method', 'limits']
```

而渲染导航用的 `links` 数组有 9 项，含 `compare`、`lab`、`timeline`。两个列表不同步，滚到这三节时 `current` 永远落不进去，高亮停在上一个命中的 `stats`（普查）。

进度条一直正常，说明滚动监听本身没问题，只是高亮判定漏了项。

### 实测证据（修复前）

逐节滚动，读取 `.topnav__item--active` 的文本：

| 滚到章节 | 高亮项 | 进度条 |
|---|---|---|
| top | 首页 ✓ | 0.6% |
| cosmos | 首页（预期） | 12.9% |
| pipeline | 流水线 ✓ | 25.5% |
| funnel | 漏斗 ✓ | 35.6% |
| stats | 普查 ✓ | 45.4% |
| **compare** | **普查 ✗** | 52.9% |
| **lab** | **普查 ✗** | 58.6% |
| **timeline** | **普查 ✗** | 71.6% |
| method | 方法 ✓ | 87.4% |
| limits | 边界 ✓ | 98.4% |

### 修法

把章节列表提为模块级常量 `NAV_SECTIONS`，导航渲染与滚动判定都从它派生，从结构上消除两处列表漂移的可能。

`#cosmos`（星系本身）**不**加入该列表：导航里没有它的入口，加进去会产生一个没有任何导航项能对应的高亮值，所以滚到星系时保持「首页」高亮是有意为之。

## 问题 2：标题旁的分子动画左侧被裁

### 布局事实

- `.app`：`max-width: 1180px; padding: 0 24px` → 内容列宽 **1132px**
- `.hero`：`position: relative; overflow: hidden; display: grid; place-items: center; padding: 120px 0 80px`
- `.hero__glow`（`inset: -20%`）、`.hero__stars`（`inset: 0`）是 `.hero` 的直接子元素，靠 `overflow: hidden` 兜住，不能删
- `.hero__inner`：`position: relative; max-width: 860px`，在 `.hero` 里居中 → 左右各留 **136px** 空档
- `.hero__molecule-slot`：`.hero__inner` 的第一个子元素，`position: absolute; top: 58px; left: calc(50% - 600px); width: 240px; height: 240px`

`left: calc(50% - 600px)` 相对 860px 的 inner 算出 −170px，即 `slot.left = inner.left − 170 = hero.left − 34`，**34px 落在 `.hero` 外面被 `overflow: hidden` 裁掉**。分子在 240px 框内的墨迹跨度约 14..230px，因此左侧约 20–24px 的原子被切（推算，与肉眼观察到的「左边缺一块」一致）。

### 实测：不同视口下被裁多少（修复前）

| 视口宽 | slot 左缘 | .hero 左缘 | 被裁 |
|---|---|---|---|
| 1920 / 1600 / 1440 / 1366 / 1280 / 1200 | 353 / 193 / 113 / 76 / 33 / −7 | 387 / 227 / 147 / 110 / 67 / 27 | 34 |
| 1150 | −32 | 24 | **57** |
| 1105 | −55 | 24 | **79** |

1228px 以上 `.app` 已到 1180 上限（内容列恒为 1132），裁切量恒为 34px；视口窄于 1228px 后 `.app` 开始收缩，inner 与 hero 之间的空档变小，裁切量线性增大。

### 实测：往右移多少能修好

对 `left` 施加不同增量，记录裁切量，并用 `Range.getClientRects()` 量标题的**实际字形边界**（不是 860px 的块盒）判断是否压字：

| 视口 | 需要的右移量 | 该量下是否压标题字形 |
|---|---|---|
| 1920 / 1600 / 1440 / 1366 / 1280 / 1228 / 1200 | **+40px**（裁切归零） | 否 |
| 1150 | +60px | 否 |
| 1105 | +80px | 压到 4px |

`+80px` 在 1228px 及以上会开始压标题首字，所以不能统一用一个数字。

### 修法（两条规则）

1. 主规则：`left: calc(50% - 560px)`（即原值右移 40px）
2. `@media (min-width: 1101px) and (max-width: 1227px)`：`left: calc(50% - 520px)`，盒子从 240² 缩到 208²
   - 代入实测：1150 → 槽位 48..256（hero 左缘 24，裁切 0；标题字形 278，不相交）
   - 1105 → 槽位 25..233（裁切 0；标题字形 261，不相交）
3. `≤1100px` 不动：该区间分子已是 `position: relative` 居中放在标题上方

## 已确认但不打算动的点

- `#cosmos` 不进导航判定，保持「首页」高亮
- `.hero` 的 `overflow: hidden` 保留（背景光晕 `inset: -20%` 靠它兜住，去掉会出横向滚动条）
- 不新增 WebGL 上下文：标题分子一直是 2D canvas
